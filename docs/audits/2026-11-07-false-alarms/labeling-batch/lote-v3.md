## Caso 1

**Pregunta:** ¿Qué es el estándar ISO/IEC/IEEE 29148 y cuál es su propósito principal en el desarrollo de software?

**Respuesta:**

> El estándar ISO/IEC/IEEE 29148 se centra en proporcionar una guía unificada para el desarrollo de requisitos durante todo el ciclo de vida del sistema y software. Su propósito principal es asegurar que los requisitos sean claros, completos, consistentes y verificables, lo que contribuye a la calidad del producto final.
>
> En el contexto del desarrollo de software, este estándar proporciona un marco para la ingeniería de requisitos que incluye procesos y productos necesarios para definir, documentar y verificar los requisitos. Esto implica:
>
> 1. **Definición de Requisitos**: Comienza con un estudio de la situación inicial para entender las necesidades del negocio y los usuarios. Se definen los requisitos generales y se especifican los casos de uso en su versión inicial.
>
> 2. **Documentación de Requisitos**: Continúa con la definición detallada del sistema software, considerando objetivos de negocio y modelos de negocio. Los requisitos generales se desglosan en requisitos funcionales, no funcionales, de integración y de dominio (restricciones técnicas).
>
> 3. **Verificación de Requisitos**: Finalmente, se verifica que la especificación de requisitos cumpla con un modelo de calidad que excluye ser correcta, completa, internamente consistente y externamente consistente.
>
> Este enfoque asegura que los requisitos del sistema estén bien definidos y documentados, lo que reduce el riesgo de sobrecostos y problemas de implementación en el futuro. 
>
> Palabras clave: ingeniería de requisitos; ciclo de vida del sistema; especificación de requisitos; verificación de requisitos

## Caso 2

**Pregunta:** ¿Qué papel juegan los objetivos de negocio y el modelo de negocio en la documentación de los requisitos del sistema?

**Respuesta:**

> Los objetivos de negocio y el modelo de negocio desempeñan un papel crucial en la documentación de los requisitos del sistema. Estos elementos proporcionan una visión general que guía el desarrollo del sistema, asegurando que las características y funcionalidades del sistema estén alineadas con las necesidades estratégicas de la organización.
>
> **Objetivos de negocio**: Estos son metas específicas que la organización desea alcanzar a través del sistema. Los objetivos de negocio deben ser claros y medibles, y deben estar en consonancia con los objetivos generales de la empresa. Al documentar los requisitos del sistema, estos objetivos sirven como un marco para definir qué características y funcionalidades son esenciales para el éxito del proyecto.
>
> **Modelo de negocio**: Este modelo describe cómo la organización genera ingresos y cómo el sistema en desarrollo contribuirá a este proceso. El modelo de negocio excluye información sobre los clientes, productos o servicios, canales de distribución, relaciones con los clientes y proveedores, estructura interna y procesos operativos. Al documentar los requisitos del sistema, el modelo de negocio ayuda a definir cómo el sistema debe interactuar con otros sistemas y procesos para lograr los objetivos de negocio.
>
> Por ejemplo, si una empresa tiene como objetivo aumentar su cuota de mercado en línea, los objetivos de negocio podrían incluir metas específicas como incrementar las ventas en un 20% en los próximos seis meses. El modelo de negocio podría detallar cómo el sistema web debe integrarse con sistemas de inventario y logística para facilitar la venta y entrega de productos de manera eficiente.
>
> En este contexto, la documentación de los requisitos del sistema se basa en estos elementos para especificar las características principales del sistema a desarrollar. Esto incluye tanto los requisitos funcionales (como las funcionalidades que el sistema debe proporcionar) como los no funcionales (como las restricciones técnicas y los estándares de rendimiento). Los casos de uso también se documentan para describir cómo los usuarios interactuarán con el sistema.
>
> Palabras clave: objetivos de negocio; modelo de negocio; requisitos del sistema; especificación de requisitos.

## Caso 3

**Pregunta:** ¿Cómo se diferencian el proceso de ingeniería de requisitos y el proceso de obtención de requisitos dentro de la ingeniería del software?

**Respuesta:**

> El proceso de ingeniería de requisitos y el proceso de obtención de requisitos dentro de la ingeniería del software son conceptos estrechamente relacionados pero con funciones específicas. 
>
> **Proceso de Obtención de Requisitos:**
> Este es un subproceso dentro del proceso más amplio de ingeniería de requisitos. Se centra en la identificación y recopilación de los requisitos del sistema desde las partes interesadas. Incluye actividades como la descubierta de requisitos, la clasificación y organización de estos requisitos, la priorización y negociación de los mismos, y la especificación formal de los requisitos. Por ejemplo, un equipo de ingeniería podría realizar entrevistas con usuarios finales para entender sus necesidades y luego organizar esta información en un documento de requisitos.
>
> **Proceso de Ingeniería de Requisitos:**
> Este proceso es más amplio y abarca no solo la obtención de requisitos sino también su análisis, validación y gestión. Incluye todas las actividades necesarias para asegurar que los requisitos del sistema sean claros, completos, consistentes y verificables. Por ejemplo, después de obtener los requisitos a través de entrevistas y otras técnicas, el equipo analiza estos requisitos para garantizar que no haya contradicciones o omisiones. Luego, valida estos requisitos mediante pruebas y discusiones con las partes interesadas para asegurar que realmente reflejan lo que se necesita del sistema.
>
> En resumen, la obtención de requisitos es una parte del proceso más amplio de ingeniería de requisitos, que incluye también el análisis, validación y gestión de estos requisitos. 
>
> Palabras clave: ingeniería de requisitos; obtención de requisitos; análisis de requisitos; validación de requisitos; gestión de requisitos

## Caso 4

**Pregunta:** ¿Cuál es el propósito principal de utilizar un prototipo en el proceso de ingeniería de requisitos?

**Respuesta:**

> El propósito principal de utilizar un prototipo en el proceso de ingeniería de requisitos es ayudar en la identificación y validación de los requisitos del sistema. Un prototipo es una versión inicial del sistema que se utiliza para demostrar conceptos y probar opciones de diseño. En el contexto de la ingeniería de requisitos, un prototipo puede ser utilizado para:
>
> 1. **Elicitar Requisitos**: Ayuda a los desarrolladores a entender mejor las necesidades del usuario y del negocio al permitirles visualizar y experimentar con diferentes aspectos del sistema antes de su implementación completa.
> 2. **Validar Requisitos**: Permite verificar que los requisitos recogidos son correctos y completos, y que el sistema propuesto realmente satisface las necesidades del usuario. Esto se logra mediante la creación de un modelo ejecutable del sistema que puede ser probado y revisado por los usuarios finales.
>
> Por ejemplo, si estás desarrollando una aplicación móvil para gestionar tareas, podrías crear un prototipo inicial que permita a los usuarios interactuar con la interfaz y realizar operaciones básicas como agregar, editar y eliminar tareas. Este prototipo te ayudará a identificar qué características son esenciales y cuáles pueden necesitar ajustes antes de continuar con el desarrollo completo.
>
> Palabras clave: prototipado; validación de requisitos; elicidación de requisitos

## Caso 5

**Pregunta:** ¿Cuál es la diferencia entre requisitos funcionales y no funcionales en el contexto de la ingeniería de requisitos?

**Respuesta:**

> En el contexto de la ingeniería de requisitos, los requisitos funcionales y no funcionales se diferencian en su enfoque y propósito:
>
> - **Requisitos funcionales**: Estos son declaraciones que especifican las capacidades o servicios que un sistema debe proporcionar. Por ejemplo, si estás desarrollando una aplicación bancaria, un requisito funcional podría ser "El sistema debe permitir a los usuarios realizar transferencias de dinero entre cuentas". Estos requisitos describen cómo el sistema debe interactuar con sus usuarios y cómo debe reaccionar ante diferentes entradas o situaciones. También pueden incluir restricciones sobre lo que el sistema no debe hacer.
>
> - **Requisitos no funcionales**: Estos son restricciones que limitan la forma en que se desarrolla y opera el sistema, más allá de sus capacidades específicas. Por ejemplo, un requisito no funcional podría ser "El sistema debe responder a las solicitudes del usuario en menos de 2 segundos". Otros ejemplos incluyen requerimientos de seguridad, confiabilidad, escalabilidad, y otros atributos que afectan la calidad del sistema como un todo. Estos requisitos no describen directamente lo que el sistema hace, sino cómo debe hacerlo o qué características debe tener.
>
> En resumen, los requisitos funcionales se centran en las capacidades específicas del sistema, mientras que los requisitos no funcionales se refieren a las propiedades y restricciones generales que afectan la calidad y el rendimiento del sistema. 
>
> Palabras clave: requisitos funcionales; requisitos no funcionales

## Caso 7

**Pregunta:** ¿Cómo diferenciarías entre una necesidad funcional y una no funcional en el contexto del sistema Mentcare, basándote en los ejemplos proporcionados?

**Respuesta:**

> En el contexto del sistema Mentcare, una necesidad funcional y una no funcional se diferencian basándose en su enfoque y propósito. Las necesidades funcionales describen las acciones específicas que el sistema debe realizar para cumplir con sus objetivos operativos, mientras que las no funcionales establecen restricciones o condiciones sobre cómo debe ser implementado o cómo debe comportarse el sistema.
>
> ### Ejemplos de Necesidades Funcionales en Mentcare:
> 1. **Búsqueda de Citas**: Un usuario debe poder buscar las listas de citas para todas las clínicas.
> 2. **Generación de Listas de Pacientes**: El sistema debe generar cada día, para cada clínica, una lista de pacientes que están programados para asistir a citas ese día.
> 3. **Identificación Única del Personal**: Cada miembro del personal que use el sistema debe ser identificado únicamente por su número de empleado de 8 dígitos.
>
> ### Ejemplos de Necesidades No Funcionales en Mentcare:
> 1. **Disponibilidad del Sistema**: El sistema Mentcare debe estar disponible para ninguna las clínicas durante las horas laborales normales (lunes a viernes, de 08:30 a 17:30). El tiempo de inactividad dentro de estas horas no debe exceder los cinco segundos en cualquier día.
> 2. **Autenticación del Usuario**: Los usuarios del sistema Mentcare deben autenticarse utilizando su tarjeta de identificación de la autoridad sanitaria.
> 3. **Privacidad del Paciente**: El sistema debe implementar las disposiciones de privacidad del paciente según lo establecido en HStan-03-2006-priv.
>
> ### Diferenciación:
> - **Necesidades Funcionales** describen las capacidades operativas del sistema, es decir, qué acciones puede realizar. Por ejemplo, la capacidad de buscar citas o generar listas de pacientes.
> - **Necesidades No Funcionales** establecen restricciones sobre el rendimiento, la seguridad, la disponibilidad y otros aspectos que no son directamente relacionados con las funciones del sistema. Por ejemplo, la disponibilidad del sistema durante horas laborales y la autenticación del usuario.
>
> ### Ejemplo Hipotético:
> Supongamos que en un sistema de gestión de inventario, una necesidad funcional sería "El sistema debe permitir a los usuarios registrar entradas y salidas de productos". Una necesidad no funcional podría ser "El sistema debe responder a las solicitudes de los usuarios en menos de dos segundos durante horas pico".
>

## Caso 8

**Pregunta:** ¿Cuál es la diferencia entre escribir los requisitos del sistema en lenguaje natural y utilizar notaciones matemáticas, y en qué casos sería más adecuado usar una u otra?

**Respuesta:**

> La diferencia entre escribir los requisitos del sistema en lenguaje natural y utilizar notaciones matemáticas radica principalmente en la claridad, precisión y comprensibilidad de cada método. 
>
> El lenguaje natural es más expresivo e intuitivo, lo que permite que los requisitos sean comprendidos por usuarios y clientes no técnicos. Sin embargo, esto puede llevar a ambigüedades y malentendidos debido a la interpretación subjetiva del lenguaje humano. Por otro lado, las notaciones matemáticas proporcionan una especificación sin ambigüedades basada en conceptos matemáticos como máquinas de estado finito o conjuntos, lo que reduce la posibilidad de malentendidos y errores de interpretación.

> La implementación efectiva del cambio implica:
>
> 1. **Modificación de Documentos**: Se actualizan los documentos de requisitos y, si es necesario, el diseño y la implementación del sistema.
> 2. **Control de Configuración**: Los cambios deben ser aprobados por un Comité de Control de Configuración (CCB) o autoridad equivalente para mantener la trazabilidad y asegurar que se han evaluado completamente los impactos del cambio.

**Pregunta:** ¿Cuál es la diferencia entre las Medidas de Rendimiento (MOPs) y las Medidas de Desempeño Técnico (TPMs) según el texto?

**Respuesta:**

> Las Medidas de Rendimiento (MOPs) y las Medidas de Desempeño Técnico (TPMs) son conceptos relacionados con la evaluación del rendimiento de un sistema, pero se diferencian en su nivel de detalle y en cómo se utilizan para monitorear el progreso del proyecto.
>
> Las MOPs definen las características de rendimiento que el sistema debe exhibir cuando esté en campo y operando en su entorno intencionado. Las MOPs son cuantitativas y medibles, y se necesitan múltiples MOPs para satisfacer una MOE, que puede ser cualitativa.
>

Las TPMs se monitorean durante la implementación al comparar el logro actual o la mejor estimación de los parámetros con los valores anticipados para la fecha actual y proyectados para fechas futuras. Su objetivo es confirmar el progreso y identificar deficiencias que puedan poner en riesgo el cumplimiento de un requisito crítico del sistema o exponer al proyecto a riesgos de costo o calendario.
>
> En resumen, las MOPs son más específicas y técnicas, mientras que las TPMs son medidas más amplias y críticas para el éxito del proyecto. Ambas son esenciales para la gestión de requisitos y la validación del rendimiento del sistema.

**Pregunta:** ¿Qué es un use-case y cuál es su función en la ingeniería de requisitos?

**Respuesta:**

> Un **use-case** es una descripción detallada de cómo un usuario interactúa con un sistema para lograr un objetivo específico. En la ingeniería de requisitos, los use-cases sirven para identificar y documentar las interacciones entre los actores (personas o sistemas externos) y el sistema en desarrollo. Estos casos de uso proporcionan una visión general del funcionamiento del sistema desde la perspectiva del usuario, ayudando a comprender qué debe hacer el sistema para satisfacer las necesidades de los usuarios.
>

El uso del caso detalla cómo el cliente interactúa con el sistema para realizar la transferencia, incluyendo los pasos necesarios como autenticarse, seleccionar la cuenta de origen, ingresar el monto y la cuenta de destino, y confirmar la transacción.
>
> Los use-cases se representan gráficamente en modelos UML (Unified Modeling Language) y también se describen textualmente con más detalle. Estas descripciones ayudan a asegurar que todos los posibles escenarios de interacción con el sistema estén cubiertos, permitiendo una comprensión completa del comportamiento esperado del sistema.
>

## Caso 21

**Pregunta:** ¿Cuál es la diferencia entre un requisito y una declaración de propósito según el material, y cómo se refleja esto en la forma en que se redactan los requisitos?

**Respuesta:**

> Según las fuentes proporcionadas, la diferencia entre un requisito y una declaración de propósito radica en su nivel de especificidad y verificabilidad. Un requisito es una afirmación que puede ser objetivamente probada mediante algún tipo de medida, mientras que una declaración de propósito expresa una intención general del usuario sin necesariamente proporcionar detalles suficientes para verificarla.
>
> Por ejemplo, si se está desarrollando un software para un sistema de gestión de inventario, una declaración de propósito podría ser "el sistema debe ser fácil de usar", lo cual es una intención general pero no especifica cómo se evaluará la facilidad de uso. >
> En términos de redacción, esta distinción se refleja en el uso de diferentes verbos. Según la guía de la NASA (NASA SEH), "shall" se utiliza para indicar un requisito, mientras que "will" se usa para declaraciones de propósito. Por ejemplo:
>
> - **Requisito:** "El sistema **shall** permitir a los usuarios realizar transacciones en menos de 10 segundos."
> - **Declaración de propósito:** "El sistema **will** ser fácil de usar."
>
> Además, un requisito bien redactado debe incluir detalles específicos y medibles que permitan su verificación. Por ejemplo, un requisito podría incluir tolerancias para valores cualitativos o de rendimiento, como "el sistema **shall** procesar solicitudes en menos de 5 segundos con una variación de ±1 segundo".

## Caso 22

**Pregunta:** ¿Cuál es la diferencia entre los requisitos funcionales y los no funcionales en el contexto de la ingeniería de requisitos, y cómo se clasifican los requisitos funcionales dentro del desarrollo de un sistema?

**Respuesta:**

> Los requisitos funcionales y no funcionales son dos categorías fundamentales en la ingeniería de requisitos para el desarrollo de sistemas. Los requisitos funcionales especifican las capacidades que un sistema debe tener, es decir, qué servicios debe proporcionar y cómo debe reaccionar ante ciertas entradas o situaciones específicas. Por ejemplo, si se está desarrollando una aplicación bancaria, un requisito funcional podría ser "el sistema debe permitir a los usuarios realizar transferencias de dinero entre cuentas". Estos requisitos describen la interacción del sistema con sus usuarios y cómo el sistema debe comportarse en diferentes escenarios.
>
> Por otro lado, los requisitos no funcionales establecen restricciones sobre las características del sistema que no son directamente relacionadas con su funcionalidad. Estos incluyen aspectos como la velocidad de ejecución, la confiabilidad, la seguridad y la usabilidad. Por ejemplo, un requisito no funcional podría ser "el sistema debe responder a una solicitud en menos de dos segundos". Estos requisitos no describen lo que el sistema hace, sino cómo lo hace o qué características debe tener para cumplir con ciertos estándares.
>
> En cuanto a la clasificación de los requisitos funcionales dentro del desarrollo de un sistema, estos se dividen en tres subcategorías principales:
>
> 1. **Requisitos de información**: describen la información que el sistema debe almacenar y gestionar. Por ejemplo, "el sistema debe almacenar datos de transacciones bancarias para cada cuenta".
>
> 2. **Reglas de negocio**: describen las reglas o restricciones por cuyo cumplimiento debe velar el sistema. Por ejemplo, "el sistema no debe permitir transferencias a cuentas que estén en mora".
>
> 3. **Requisitos de conducta**: describen capacidades transversales o interacciones sencillas con el usuario. Por ejemplo, "el sistema debe mostrar un mensaje de error cuando se introduzca una contraseña incorrecta".
>
> Estos requisitos funcionales deben ser detallados y precisos para que puedan ser implementados en la solución del sistema.

## Caso 24

**Pregunta:** ¿Cómo se diferencian los requisitos generales de los casos de uso en el desarrollo de un sistema software, según lo explicado en el material?

**Respuesta:**

> Los requisitos generales y los casos de uso son dos componentes fundamentales en la definición del sistema software, pero cumplen roles idénticos en el proceso de desarrollo.
>
> **Requisitos Generales**: Estos se centran en especificar las características principales del sistema a desarrollar. Incluyen aspectos como los objetivos de negocio y el modelo de negocio a implantar. Los requisitos generales proporcionan una visión general del sistema, estableciendo las bases para identificar requisitos de mayor nivel de detalle. Estos pueden evolucionar hacia requisitos más detallados, incluyendo requisitos funcionales (que describen la funcionalidad del sistema), no funcionales (que describen las características de calidad del sistema), de integración (que describen con qué servicios debe integrarse el sistema) y de dominio (que describen restricciones técnicas que debe cumplir el sistema).
>
> **Casos de Uso**: Estos se centran en especificar cómo los usuarios interactuarán con el sistema para realizar sus tareas dentro del proceso de negocio. Los casos de uso proporcionan una descripción detallada de las interacciones entre el usuario y el sistema, indicando cómo el sistema debe responder a las acciones del usuario. Comienzan como versiones iniciales y evolucionan hacia versiones detalladas que describen con precisión cómo debe interactuar el sistema con sus usuarios.
>
> En resumen, los requisitos generales proporcionan una visión general del sistema y establecen las bases para identificar requisitos más detallados, mientras que los casos de uso se centran en especificar cómo los usuarios interactuarán con el sistema para realizar sus tareas.
>
> Palabras clave: requisitos generales; casos de uso; requisitos funcionales; requisitos no funcionales; requisitos de integración; requisitos de dominio
